# Healthcare Data Quality Framework

An automated data-quality framework for a patient/encounter ETL pipeline: schema
validation, null and duplicate checks, referential integrity, and business-rule
checks (e.g. "an encounter can't happen before the patient was born") — the kind
of thing that quietly prevents bad data from reaching downstream reporting.

Built on **pandas + SQLAlchemy + PyTest**, with a **Streamlit** dashboard over the
results and an example **Airflow** DAG showing how it plugs into a scheduler.

## Why it's built this way

- **Runs anywhere with zero setup.** The pipeline defaults to a local SQLite file
  as its "warehouse." In production it's meant to run against **Snowflake or
  Databricks** instead — because every query goes through SQLAlchemy, that's a
  `WAREHOUSE_URL` environment variable, not a rewrite. See `src/db.py`.
- **The synthetic dataset has real problems in it, on purpose.**
  `src/generate_synthetic_data.py` seeds a handful of realistic data-quality bugs
  (a missing birth date, an invalid gender code, an orphaned encounter, a
  duplicate encounter ID) into an otherwise-fabricated dataset. That means the
  test suite can prove the checks actually catch problems, not just that they
  compile.
- **Unit tests and integration tests are separated on purpose.**
  `tests/test_quality_checks.py` pins down each check's logic against small,
  hand-built DataFrames. `tests/test_pipeline_integration.py` runs the real ETL
  against the committed dataset and asserts the seeded issues are the *specific*
  ones caught — nothing more, nothing fewer.
- **No real patient data.** Every row is generated by Faker with a fixed seed
  (`SEED = 20260824`), so the dataset is reproducible and entirely fabricated.

## Architecture

```
data/raw/                    Synthetic patients.csv, encounters.csv, conditions.csv
src/generate_synthetic_data.py  Seeded Faker generator (re-run with --regenerate)
src/db.py                     SQLAlchemy engine factory (SQLite locally, Snowflake/Databricks via env var)
src/etl.py                    raw -> staging -> curated (patient_encounter_summary)
src/quality_checks.py         The rule engine: schema, null, unique, referential
                               integrity, valid-enum, row-count reconciliation,
                               business-rule checks
src/report.py                 JSON report + append-only history log
pipeline.py                   CLI entrypoint: ETL -> checks -> report, exit code
                               reflects pass/fail
tests/test_quality_checks.py       Unit tests for each check function
tests/test_pipeline_integration.py Integration tests against the real dataset
dashboard/app.py              Streamlit dashboard over the report history
orchestration/airflow_dag_example.py  Illustrative production DAG (not run in CI)
.github/workflows/ci.yml      Runs the test suite (the actual gate) + a demo pipeline run
```

## Tech stack

Python · pandas · SQLAlchemy · PyTest · Faker · Streamlit · Airflow (illustrative) ·
Snowflake / Databricks (production target) · GitHub Actions

## Running it locally

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python pipeline.py --regenerate     # (re)generate synthetic data, run ETL + checks
```

This prints a pass/fail summary and writes `reports/latest_quality_report.json`
plus an append-only `reports/quality_report_history.jsonl`.

Point it at a real warehouse instead of local SQLite:

```bash
export WAREHOUSE_URL="snowflake://user:pass@account/DATABASE/SCHEMA?warehouse=WH"
python pipeline.py
```

### Dashboard

```bash
streamlit run dashboard/app.py
```

### Tests

```bash
pytest -v
```

## What the checks actually catch, right now

Running `python pipeline.py --regenerate` against the committed dataset reports
9 of 13 checks passing — the other 4 are the issues deliberately seeded into the
demo data (see "Why it's built this way" above), each one caught by exactly the
check designed to catch it. That's the point: this isn't a suite that always
prints green, it's one that tells the truth about the data.

## What this is not

Production Airflow and Snowflake/Databricks credentials aren't wired into this
repo's CI — `orchestration/airflow_dag_example.py` and the `WAREHOUSE_URL` env var
in `src/db.py` show exactly how it plugs into them, but this repo runs locally by
design so it works with zero external accounts.
